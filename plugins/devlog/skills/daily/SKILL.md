# devlog — 오늘 배운 것을 블로그 글로

수업 코드를 읽고, 핵심을 요약하고, 초보자용 주석을 달고, 코드가 만든 이미지·영상을 코드 아래에 붙여서
블로그에 올릴 수 있는 글 한 편으로 만든다. 독자는 "이 주제를 처음 보는 사람"이라고 가정한다.

## 만들어지는 것

작업 루트(git 최상위 폴더, 없으면 현재 폴더) 아래 `devlog/` 폴더에만 쓴다.

- `devlog/YYMMDD.md` — 정본. GitHub·벨로그·노션·티스토리(마크다운 모드)용
- `devlog/YYMMDD.html` — 마크다운을 못 받는 에디터(네이버 블로그 등)에 붙여넣는 용. 이미지가 파일 안에 들어 있다
- `devlog/assets/YYMMDD/` — 일지에 쓴 이미지와 영상 썸네일

원본 코드는 수정하지 않는다. 일지에 실리는 주석 단 코드는 사본이다. 수업 코드는 git에 올리기 전인 경우가 많아서,
원본에 주석을 덮어쓰면 되돌릴 방법이 없다.

## 진행 순서

### 1. 날짜와 작업 루트 정하기

- 사용자가 `261019`, `2026-10-19`, `어제`처럼 날짜를 주면 그 날짜, 없으면 오늘. 오늘 날짜가 불확실하면
  `python -c "import datetime; print(datetime.date.today())"`로 확인한다. `YYMMDD`는 2026-10-19 → `261019`.
- 작업 루트는 `git rev-parse --show-toplevel`로 찾고, 실패하면 현재 폴더.
- 사용자가 강의 메모를 함께 줬다면 3단계에서 우선 사용한다.

### 2. 대상 코드 모으기

- 루트 바로 아래에서 `YYMMDD_`로 시작하는 폴더·파일을 찾는다. 폴더 이름이 `.py`로 끝나도 폴더면 안으로 들어간다.
  안에서 코드 파일(`.py .js .html .css`)을 번호 순서로 모은다. `.ipynb`는 코드 셀만 읽는다(출력 셀의 이미지는 아직 지원하지 않는다).
- 그런 이름이 없으면 그 날짜에 수정된 코드 파일로 대신한다. `.git`, `node_modules`, `__pycache__`, `runs`, `devlog`, `.claude`는 제외.
- 하나도 없으면 날짜가 맞는지 한 줄로 되묻는다. 파일이 많으면(10개 이상) 모두 설명하지 말고 주제별로 묶어서, 글이 "오늘의 주제" 단위로 읽히게 한다.

### 3. 읽고 요약하기

- 코드를 읽고 오늘 새로 나온 개념(라이브러리, 함수, 파라미터)을 찾는다. 요약은 개념 3~5개, 각 1~2문장.
- 코드에서 알 수 없는 것(강사가 한 말, 수업 맥락)은 지어내지 않는다. 일지는 나중에 복습하는 자료라서 틀린 설명이 섞이면
  안 쓰느니만 못하다. 모르는 부분은 "헷갈린 점"에 질문으로 남긴다.

### 4. 중요 코드를 고르고 주석 달기

**고르기.** 파일마다 핵심 블록 하나(길어도 25줄 안팎), 그날 처음 나온 개념이 든 부분을 고른다. import 나열이나 반복되는 틀은 뺀다.
독자는 읽는 사람이라 전체 코드를 붙이면 요점이 묻힌다. 자를 때는 함수 하나, 단계 하나처럼 **완결된 단위**로 자른다
(중간에서 자르면 읽기도 어렵고 7단계의 검증도 못 한다).

**달기.** 목표는 "이 코드를 처음 보는 사람이 왜 이렇게 쓰는지 이해하는 것"이다.

- 줄마다 달지 말고 덩어리에 단다. 블록 위에 "이 부분이 하는 일" 1~2줄, 헷갈릴 만한 줄 끝에 짧게.
- "무엇"이 아니라 "왜/무슨 개념"을 쓴다. `# 이미지를 읽는다`는 코드를 되풀이할 뿐이다.
- 처음 나온 용어는 한 줄로 풀이하고, 파라미터는 값의 의미를 쓴다(`beta=50` → 밝기를 +50). 비유는 필요할 때 한 번만.
- 기존 주석은 그대로 둔다. 그 사람의 말투와 이해가 담긴 기록이라서, 오타가 있어도 고치지 않고 필요하면 아래에 보충한다.
- 코드는 한 글자도 바꾸지 않는다. 주석(`#`)과 빈 줄, 줄바꿈만 추가한다. 변수 이름 변경, docstring 추가, 버그 수정도 하지 않는다.
  학습자의 코드를 조용히 고치면 "왜 안 됐는지" 배울 기회가 사라지고 일지의 '막힌 점' 소재도 사라진다.
  인자를 줄마다 나눠 주석을 달 때도 마지막 인자 뒤에 쉼표를 새로 붙이지 않는다(7단계의 검사기는 쉼표 하나도 코드 변경으로 본다).
- 버그나 오타로 보이는 것을 발견하면 고치지 말고, 글에도 넣지 말고, 최종 보고에서 채팅으로 알린다. 어디가, 왜 문제로 보이는지, 어떻게 고치면 되는지.
  확실하지 않으면 "~일 수 있다"로 쓴다. 작성 중인 파일일 수도 있기 때문이다. 코드 주석에도 문제를 지적하는 문장은 쓰지 않고 코드가 하는 일만 설명한다.
- API 키, 토큰, 클라이언트 ID, 비밀번호가 보이면 `YOUR_API_KEY` 같은 자리표시자로 바꾼다. 블로그는 공개되는 곳이다.

예시 (원본 → 일지에 싣는 사본):

```python
# 원본
img = cv2.imread("img.jpg")
bright = cv2.convertScaleAbs(img, alpha=1, beta=50)

# 사본
# [이미지 읽기] 사진 파일을 숫자 표(NumPy 배열)로 불러옵니다. 파일을 못 찾으면 None이 됩니다.
img = cv2.imread("img.jpg")
# [밝기 조절] 새 픽셀값 = 원래 값 × alpha + beta. beta=50이면 모든 픽셀이 50만큼 밝아집니다(255를 넘으면 255로 고정).
bright = cv2.convertScaleAbs(img, alpha=1, beta=50)
```

### 5. 결과물(이미지·영상) 찾기

```
python "<SKILL_DIR>/scripts/find_outputs.py" 코드1 코드2 ... --root "<루트>" --date YYYY-MM-DD \
    --log-dir "<루트>/devlog" --assets "<루트>/devlog/assets/YYMMDD"
```

`<SKILL_DIR>`는 이 스킬이 호출될 때 안내되는 Base directory다. `python`이 없으면 `python3`를 쓴다.
스크립트가 하는 일: 코드에 적힌 저장 경로(변수에 담은 경우 포함), YOLO `save=True`의 `runs/` 결과, 직접 캡처해 둔 `devlog/shots/` 파일을 찾고,
**그날 만들어진 파일만** 결과로 인정한다. 옛 파일을 결과로 착각하면 일지가 거짓이 되기 때문이다.

- 출력된 `outputs[].markdown`을 해당 코드 블록 **바로 아래**에 그대로 붙인다. 경로를 직접 만들지 않는다
  (공백·한글·드라이브 때문에 틀리기 쉬워서 스크립트가 만든 값을 쓴다). 캡션은 `*그림 N — 무엇을 보여주는지*` 형식으로 붙인다.
- `confidence`가 `high`인 것만 글에 넣는다. `medium`은 입력 파일(모델에 넘긴 사진·영상 등)이 결과로 둔갑했을 수 있어서 `markdown`이 `null`로 온다.
  글에 넣지 말고 최종 보고에 후보로 나열해 사용자가 확인하게 한다. 확인받은 뒤 같은 명령에 `--include-medium`을 붙여 다시 실행하면
  글에 넣을 `markdown`이 만들어진다. 공개 글에 입력 사진을 결과라고 싣는 것보다 결과 하나를 빠뜨리는 편이 낫다.
- `warning`(썸네일을 못 만든 이유 등)은 보고에 포함한다. "cv2가 없다"는 경고가 나오면 OpenCV가 설치된 파이썬(수업에서 ultralytics를 설치한 환경)으로
  같은 명령을 다시 실행해 본다. `conda env list`로 환경을 찾고 `<그 환경의 python> -c "import cv2"`로 확인하면 된다. 못 찾으면 영상은 링크로만 들어간다.
- `--assets`를 빼면 아무것도 복사하지 않고 찾기만 한다(미리 보기). 처음 쓰거나 결과가 의심스러울 때 이 방식으로 먼저 확인해도 좋다.
- `outputs`가 비면 `notes`를 읽는다. 화면에만 표시되는 코드(imshow, plt.show, gradio, streamlit)가 흔하다.
  이때 이미지를 지어내거나 비슷해 보이는 다른 파일을 끌어다 쓰지 않는다. 글에는 `> 이 코드의 결과는 화면에만 표시됩니다.` 정도만 쓰고,
  최종 보고에서 "화면을 캡처해 `devlog/shots/`에 코드 파일 접두사로 저장하면 다음에 자동으로 붙는다"(예: `v05_07.png`)고 알려 준다.
- 영상은 블로그에 따로 올려야 하는 경우가 많아서 썸네일 + 원본 링크로 들어간다.
  윈도우의 YOLO는 영상을 `.avi`로 저장하는데 브라우저에서 재생되지 않는 경우가 많다.

### 6. 글 쓰기

말투는 합니다체가 기본이고, 사용자가 지정하면 따른다. 비어 있는 섹션은 "없음"이라고 쓰지 말고 통째로 뺀다.
표는 쓰지 않고(블로그 에디터에서 깨진다) 목록은 한 단계만 쓴다. 첫 줄의 `#` 제목이 HTML의 제목이 된다.

````markdown
# 2026-10-14 개발일지 — {오늘의 주제 한 줄}

> {하루 요약 1~2문장}

## 오늘 배운 것
- **{개념}** — {1~2문장}

## 코드로 보기
### 1. {이 코드가 하는 일} (`파일명.py`)
{무엇을 하는 코드인지 2~3문장}

```python
{주석 단 핵심 코드}
```

{outputs[].markdown}
*그림 1 — {무엇을 보여주는지}*

## 막혔던 점과 해결
## 헷갈린 점 → 내일 확인할 것
````

"막혔던 점"과 "헷갈린 점"은 **사용자가 메모로 알려 준 것만** 쓴다. 이 글은 사용자의 블로그에 올라가는 사용자의 글이라서,
모델이 발견한 문제나 평가, 추측한 질문을 섞지 않는다. 코드에서 버그·오타를 발견하면 글에는 넣지 않고(고치지도 않고)
8단계의 최종 보고에서 채팅으로만 알린다. 사용자가 원하면 그때 글에 넣는다.

`devlog/YYMMDD.md`가 이미 있으면 덮어쓰지 말고 `YYMMDD_2.md`로 저장한다. 사용자가 직접 다듬었을 수 있다.

### 7. 검증하기

1. **코드가 그대로인지.** 주석 단 파이썬 조각마다 원본 조각과 비교한다. 두 조각을 임시 폴더에 파일로 저장해(작업 폴더에 임시 파일을 남기지 않는다)
   `python "<SKILL_DIR>/scripts/check_same_code.py" 원본조각 주석본조각`을 실행한다. 다르다고 나오면 주석 단 쪽을 원본에 맞게 고친다.
   파이썬이 아닌 코드는 도구가 없으니 코드 줄이 그대로인지 직접 대조한다.
2. **HTML 만들기.** `python "<SKILL_DIR>/scripts/build_html.py" "<루트>/devlog/YYMMDD.md"`.
   종료 코드 2는 키처럼 보이는 문자열이 있다는 뜻이다. 해당 줄을 자리표시자로 바꾸고 다시 실행한다. 이 검사는 마지막 안전망이고, 1차 책임은 4단계에 있다.

### 8. 최종 보고

짧게 쓴다: 만든 파일 경로, 결과물을 붙인 코드 수, 사용자가 확인할 것(글에 넣지 않은 `medium` 후보 목록, 화면 출력만 있는 코드, 썸네일 경고, 발견한 문제), 올리는 방법 한 줄.
블로그에 올리는 방법을 물으면 `references/blog-guide.md`를 읽고 그 블로그에 맞게 답한다.
